# 非凸α无人机二次开发文档包设计

日期：2026-04-21

## 1. 背景

当前仓库不是单一源码仓，而是由以下几类材料组成的复合资料库：

- 实机探查快照
- 机上源码快照
- PDF 说明书
- 在线 wiki
- 已整理的本地知识库

后续工作目标不是补一份“好读一点”的说明书，而是沉淀一套可直接支撑二次开发、联调、排障和后续交接的完整文档包。

本设计明确拒绝 “先做一个 MVP 版本再补” 的路线。后续交付按完整版本设计，一次性把部署边界、接口事实、截图材料、开发入口和验收标准拉齐。

## 2. 目标

本次文档包设计目标如下：

- 明确这台机器当前实际部署了哪些功能，哪些仅存在于产品线宣传、wiki 或源码中
- 明确后续二开时可以接入的接口、输入、输出、消息格式和前置条件
- 明确启动链、运行链、参数入口和风险边界
- 为开发同事提供一套可检索、可复核、可长期维护的事实源
- 降低后续接手者对“口头传帮带”的依赖

## 3. 读者优先级

本次文档包第一读者为二次开发和系统集成同事，而不是日常飞行同事。

读者优先级如下：

1. 二次开发同事
2. 联调与排障同事
3. 日常使用和飞行同事

这意味着文档结构必须优先回答以下问题：

- 当前机器到底部署了什么
- 哪个脚本会拉起哪些节点
- 哪些 topic 和消息格式是当前真实可用的
- 如果我要接一个上层系统，最小输入输出是什么
- 如果我要改行为，应该改 YAML、任务层、规划层还是控制层

## 4. 当前机器事实边界

### 4.1 事实基线

以下判断以 2026-04-21 的本地快照为主事实源：

- `uav/03-drone-snapshot/uav_probe_20260421_120809`
- `uav/03-drone-code/snapshot_20260421_174511`
- `uav/10-knowledge-base/*.md`

在线 wiki 和 PDF 作为补充事实源使用，但不得覆盖实机快照。

### 4.2 当前主链判断

当前机器的主链为：

- `mavros`
- `px4ctrl`
- `multipoint`
- `Diff-planner`
- `faster-lio`
- `VINS-Fusion-gpu`
- `realsense-ros`

当前事实更支持 `D435 + VINS` 作为视觉定位主链，而不是 `usb_cam + Elastic` 作为当前实机主链。后续实施阶段应继续按源码快照和实机快照复核这一点，但文档主路径不得把 Elastic 视为当前默认部署链路。

### 4.3 当前部署边界

当前应纳入主文档主路径的功能：

- 单机 LIO 定位
- 单机 VIO 定位
- 单机规划与轨迹执行
- 自动起飞、返航、降落
- 多点任务
- 状态观测与排障
- 遥控器接管和安全切换

当前不纳入主路径，但可作为扩展或附录说明的功能：

- Elastic / 目标跟踪
- FUEL / 自主探索
- Formation / 集群
- YOLO 检测

### 4.4 文档边界规则

后续所有交付件必须显式区分三类状态：

- `当前实机已部署并可直接验证`
- `源码存在但当前不作为实机主流程`
- `wiki/PDF 提到但当前实机未部署`

禁止把产品线能力和实机能力混写。

## 5. 事实源优先级

为避免后续文档出现相互冲突，统一规定事实源优先级如下：

1. 实机探查快照
2. 机上源码快照
3. 本地知识库中的已校正文档
4. PDF 说明书
5. 在线 wiki

若高优先级与低优先级冲突，按高优先级结论写入文档，并在备注中记录偏差。

## 6. 交付件设计

完整版本包含 5 个主件和 1 组维护源文件。

### 6.1 主件 1：Developer Guide

格式：

- 对外交付：Word
- 仓库存档：Markdown

职责：

- 作为整套文档包的主叙述载体
- 系统性解释架构、链路、接口、参数和扩展建议

章节固定为：

1. 机器现状总览
2. 当前已部署功能清单
3. 启动链与运行链
4. 接口说明
5. 关键参数入口
6. 状态观测与排障路径
7. 二开建议与扩展边界
8. 截图与状态对照附录索引

### 6.2 主件 2：接口总表

格式：

- 主格式：Excel
- 摘要版：Word 或 Markdown 摘要表

职责：

- 作为所有接口的主速查件
- 支撑筛选、排序、后续补录和长期维护

### 6.3 主件 3：功能-部署矩阵

格式：

- Excel

职责：

- 统一“当前实机能力”和“产品线能力”的边界认知
- 作为是否进入主速查材料的准入表

### 6.4 主件 4：截图与状态对照附录

格式：

- Word 主附录
- 原始素材清单可附 Excel

职责：

- 集中展示关键状态下的遥控器、rviz、终端和 topic 观测方式
- 补齐现有资料中截图分散、状态不成体系的问题

### 6.5 主件 5：开发导航页

格式：

- Word 一页摘要
- Markdown 同步存档

职责：

- 回答“我想改什么，应该看哪里”
- 帮助新开发者快速跳转到正确文档和正确代码层

### 6.6 维护源文件

格式：

- Markdown

职责：

- 作为仓库内可 diff、可审阅、可版本控制的事实源
- 为后续 Word / Excel 更新提供上游内容基础

## 7. Developer Guide 结构设计

### 7.1 机器现状总览

需要回答：

- 机载电脑、系统、ROS、MAVROS、网络、工作空间分别是什么
- 当前主链模块有哪些
- 当前未部署模块有哪些
- 与 PDF / wiki 相比有哪些关键偏差

### 7.2 当前已部署功能清单

每个功能统一按以下字段描述：

- 功能名
- 当前状态
- 依赖硬件
- 主启动方式
- 关键输入
- 关键输出
- 典型验证方式
- 风险与注意事项

主清单至少包含：

- LIO 定位
- VIO 定位
- 单机规划
- 多点任务
- 自动起飞
- 自动返航
- 自动降落
- 状态观测
- 遥控器接管

### 7.3 启动链与运行链

必须给出两种视图：

- `脚本 -> launch -> node -> topic`
- `功能 -> 依赖模块 -> 启动入口 -> 可见状态`

至少覆盖：

- `run_single_lio.sh`
- `run_single_vio.sh`
- `run_lio.sh`
- `run_vins.sh`
- `takeoff.sh`
- `pub_trigger.sh`
- `back.sh`
- `land.sh`

### 7.4 接口说明

接口说明按层次组织，而不是按字母顺序堆砌。

必须分为：

- 人工物理层
- 脚本编排层
- ROS 动作层
- ROS 状态观测层
- 配置入口层
- 扩展接入层

### 7.5 关键参数入口

至少覆盖：

- `points.yaml`
- `multipointplan_exp_lio.launch`
- `multipointplan_exp_vio.launch`
- `run_exp_single_lio.launch`
- `run_exp_single_vio.launch`
- `ctrl_param_fpv.yaml`

每个参数入口需要说明：

- 文件职责
- 常改参数
- 默认值
- 影响范围
- 风险级别
- 适合谁改

### 7.6 状态观测与排障路径

要回答：

- 看电量去哪里
- 看飞控状态去哪里
- 看定位是否正常去哪里
- 看任务是否在执行去哪里
- 看遥控器是否处于安全状态去哪里

同时给出排障顺序建议：

1. 启动脚本是否完整执行
2. 关键节点是否存在
3. 关键状态 topic 是否存在
4. 定位链是否活着
5. 控制链是否收到了命令
6. 遥控器状态是否满足自动起飞条件

### 7.7 二开建议与扩展边界

必须明确三种改造层级：

- 桥接型接入
- 任务层接入
- 规划层 / 控制层深改

并说明推荐顺序：

1. 先接 ROS 动作层与状态层
2. 再考虑替换或增强任务层
3. 最后才考虑改规划器或控制器核心

## 8. 接口总表设计

### 8.1 总体原则

接口总表不是列几个 topic 名，而是为二次开发提供“能直接接”的事实表。

每行只描述一个清晰接口对象，不混多个语义。

### 8.2 建议字段

接口总表至少包含以下字段：

- 编号
- 分类
- 名称
- 类型
- 方向
- 消息类型 / 调用格式
- 关键字段
- 上游来源
- 下游消费者
- 启动前置条件
- 典型用途
- 示例
- 当前实机状态
- 风险与注意事项
- 证据来源
- 源码定位

### 8.3 接口分类

至少分为：

- 状态观测
- 动作控制
- 配置参数
- 脚本入口
- 遥控器映射
- 调试 / 录包

### 8.4 必收录接口范围

#### 脚本入口

- `run_single_lio.sh`
- `run_single_vio.sh`
- `run_lio.sh`
- `run_vins.sh`
- `takeoff.sh`
- `pub_trigger.sh`
- `back.sh`
- `land.sh`

#### 动作接口

- `/px4ctrl/takeoff_land`
- `/move_base_simple/goal`
- `/back_trigger`
- `/goal`
- `/planning/yaw`
- `/setpoints_cmd`

#### 状态接口

- `/mavros/state`

## 10. 截图与状态对照附录设计

### 10.1 目标

解决现有资料截图分散、状态描述不集中、遥控器判断依赖经验的问题。

### 10.2 必备状态组

至少整理以下 4 组：

1. 起飞前
2. 手动悬停 / 接管
3. 自主执行
4. 返航与降落

### 10.3 每组截图必须包含的信息

- 遥控器拨杆状态
- rviz 或终端关键界面
- 建议查看的 topic
- 对应的开发判断点

### 10.4 素材缺口管理

若现有 wiki / PDF / 仓库内截图不足，则必须额外输出“待补拍素材清单”，明确：

- 需要补哪一组截图
- 需要展示哪种状态
- 拍摄时需要同时记录哪些界面

## 11. 开发导航页设计

开发导航页采用“问题 -> 入口”方式组织。

至少包含以下映射：

- 想改起飞高度 -> `ctrl_param_fpv.yaml`
- 想改航点格式 -> `points.yaml` 和 `multipointplan`
- 想接上层 Agent -> 状态接口表和动作接口表
- 想看 8 通如何触发动作 -> `multipointplan.cpp`
- 想查电量 / 状态 / 位置 -> `mavros` 状态组
- 想改任务触发方式 -> `multipoint` 和动作 topic
- 想改控制输入来源 -> `/setpoints_cmd` 与 `px4ctrl`

## 12. 学习与掌握路径

后续正文需要内嵌一条面向开发者的学习路径，分为 4 个阶段：

1. 机器画像
2. 启动链吃透
3. 接口面吃透
4. 改造点与扩展边界

每一阶段都必须有明确验收口，不能停留在“看懂一些资料”。

## 13. 交付介质设计

职责分工如下：

- Word：主文档、截图附录、开发导航页
- Excel：接口总表、功能-部署矩阵、参数索引表、素材缺口表
- Markdown：仓库内维护源稿

Word / Excel 是交付件，Markdown 是维护件。

## 14. 验收标准

### 14.1 资料完整性

以下交付件必须齐套：

- Developer Guide
- 接口总表 Excel
- 功能-部署矩阵 Excel
- 截图与状态对照附录
- 开发导航页
- Markdown 源稿

### 14.2 事实闭环

每个关键结论必须可回溯到以下一种或多种证据：

- 实机快照
- 源码
- PDF
- wiki

没有证据来源的关键结论不得进入主文档。

### 14.3 系统掌握

文档包应足以让开发者独立回答以下问题：

- 当前机器到底部署了哪些功能
- 最小启动链是什么
- 关键动作接口和消息格式是什么
- 关键状态接口和消息格式是什么
- 关键参数文件各自负责什么
- 新需求应该插在哪一层

### 14.4 二开准备度

材料应足以支撑以下任务独立开展：

- 状态观测
- 任务配置
- 外部系统接入
- 基础排障
- 扩展层级判断

## 15. 非目标

以下内容不属于本次设计直接交付范围，但可作为后续实现阶段工作：

- 直接开发 MQTT / HTTP / Agent 桥接程序
- 修改飞控参数或规划器核心逻辑
- 补拍尚未采集的实机截图
- 将所有主文档最终排版成正式对外交付版

## 16. 风险与应对

### 16.1 产品线能力与实机能力混淆

风险：

- wiki 和 PDF 容易让人误以为所有功能当前都可直接使用

应对：

- 使用功能-部署矩阵强制分栏

### 16.2 证据链不闭合

风险：

- 文档结论无法回溯到事实源，后续难以维护

应对：

- 所有表格增加 `证据来源` 列

### 16.3 截图不足

风险：

- 第二类需求无法完整闭环

应对：

- 输出单独的素材缺口清单，不以文字替代缺失截图

## 17. 下一阶段输出边界

本设计获批后，下一阶段的实施工作应包括：

- 按本设计结构输出 Developer Guide Markdown 源稿
- 整理接口总表 Excel
- 整理功能-部署矩阵 Excel
- 设计截图附录和素材缺口清单
- 输出开发导航页

实施阶段仍需遵守本设计中的事实源优先级和部署边界规则。
